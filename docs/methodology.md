# Методика обчислювальних експериментів

Опублікований зразок отримано послідовним запуском experiments/benchmark.py. Параметри груп і генератори готуються до таймованих ділянок. Для кожної детермінованої операції виконано нетаймований прогрів і п’ять окремих вимірювань, для повного перебору — три. Медіана, мінімум, максимум і кожний початковий часовий зразок містяться в docs/results/benchmark.json. Зміна часу між комп’ютерами та запусками очікувана.

Під час вимірювань автоматичне збирання циклічного сміття вимкнено. Перед повтором воно викликається поза таймером. Відлік часу починається безпосередньо перед викликом алгоритму й завершується після його повернення. Кожна відповідь зіставляється з відомим синтетичним показником; ця перевірка відбувається після завершення таймера. Пакетні запити додатково перевіряють відповіді всередині вимірюваної пакетної операції; це однаково для обох варіантів.

У групах smooth число p - 1 складається тільки з простих множників 2, 3, 5 і 7. Для safe використовується p = 2r + 1, де r просте. Прості модулі та первісні основи наведено в groups. У baseline і structure показник дорівнює p - 3, а ціль — відповідному степеню основи. Для structure у час Поліга—Геллмана входить факторизація відомого точного порядку; попередній пошук цього порядку не потрібний, оскільки використано первісну основу.

Для rho використовується квадрат первісної основи safe-групи, який має простий порядок r. Показник дорівнює ⌊3r/4⌋. Порядок надається обом алгоритмам до початку вимірювання. Для кожного модуля записано 15 траєкторій Полларда з різними зернами 8008–8022; окремого прогріву кожної траєкторії немає. У JSON наведено її час, кількість переходів і перезапусків. Три переходи відповідають одній ітерації Флойда. Підготовка 16 множників та початкового стану Полларда входить у час пошуку.

Поля operations рахують явно позначені циклічні операції. Вони не охоплюють внутрішню роботу pow, перевірку простоти, арифметику індексів або машинні інструкції інтерпретатора. table_entries у BSGS — фактична кількість ключів; у Поліга—Геллмана — найбільша з послідовно використаних таблиць компонентів. rho_restarts — число повторних стартів після першої траєкторії. ph_digits — кількість відновлених цифр у простих компонентах порядку.

table_bytes отримано окремим викликом sys.getsizeof для словника та кожного ключа й значення. Це метрика обліку об’єктів, яка не дорівнює RSS чи піковій пам’яті процесу. Спільні об’єкти малих цілих можуть враховуватися повторно. За фіксованого визначення метрика придатна для порівняння розмірів таблиці; для ліміту пам’яті платформи потрібне окреме вимірювання процесу. MiB означає 2²⁰ байтів.

Дані reuse містять двадцять показників із генератора Random(8008). fresh щоразу будує нову таблицю, reuse_with_build створює одну таблицю перед двадцятьма пошуками, queries_only вимірює двадцять пошуків після вже виконаної побудови. Для інтервальних експериментів lower і upper явно надані алгоритму: ця додаткова інформація виходить за вихідну задачу CodinGame.

У upper_bound окремо виміряно дослідницький BSGS і самодостатній файл для платформи. У elgamal усі параметри, показники та повідомлення створено для цього досліду. Дані не стосуються сторонніх ключів. Стан complete підтверджує завершення всієї серії; wall_seconds охоплює підготовку, прогріви, вимірювання та перевірки. Графіки будуються тільки з цього JSON, без симуляції часу.

Локальні результати й GitHub Actions не є прогоном прихованих тестів CodinGame. Для такого підтвердження потрібне окреме відправлення рішення на платформу.
